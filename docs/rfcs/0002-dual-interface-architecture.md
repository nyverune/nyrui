# RFC-0002: Dual-Interface Architecture (TUI + CLI Action Layer)

- **Project:** Nyrui (`nyrui`)
- **RFC:** 0002
- **Status:** Accepted
- **Type:** Architecture / API Design
- **Language:** Rust
- **Dependencies:** `nyrui-core`, `clap`, `serde`
- **Audience:** Framework maintainers and contributors
- **Last Updated:** 2026-11-12

---

## 1. Summary

This RFC specifies a unified action and dispatch architecture for Nyrui that allows an application to expose its domain operations through both an interactive Terminal User Interface (TUI) and a headless Command-Line Interface (CLI) from a single typed definition.

Instead of coupling domain mutations to TUI button callbacks or writing a parallel `clap` entrypoint that duplicates validation and service wiring, developers define typed `Action` implementations that operate on a shared `AppContext`. Nyrui uses these action definitions to:

1. **Drive TUI interactions:** Components invoke actions asynchronously via `ctx.dispatch::<A>(input)`, automatically integrating with form validation, loading states, and error modals/toasts.
2. **Drive headless CLI subcommands:** Actions annotated for CLI exposure register their `Input` schema directly into a `clap::Command` tree at startup, parse CLI flags/arguments, run without initializing `ratatui` or raw terminal mode, format the structured `Output` (`table`, `plain`, or `json`), and exit with deterministic process exit codes.

---

## 2. Motivation and Technical Problem

Developer tools built for the terminal—such as SSH identity managers (`nysh`), container dashboards, database clients, or package managers—almost always require two interaction modes:

- **Interactive Mode (TUI):** For browsing state, inspecting live logs, filling multi-step forms, and visual discovery.
- **Non-Interactive Mode (CLI):** For shell scripts, CI/CD pipelines, dotfiles automation, and quick single-shot commands (e.g., `nysh activate work-laptop` or `nysh list --format json | jq`).

In standard Rust TUI architectures, adding a CLI after building the TUI leads to three recurring defects:

1. **Split Validation and Domain Drift:** Input rules implemented in TUI form validators diverge from argument validation in the CLI parser.
2. **Accidental Terminal Initialization in Headless Environments:** Poorly separated TUI binaries initialize `crossterm::terminal::enable_raw_mode()` or `EnterAlternateScreen` before checking CLI arguments, breaking non-interactive pipes (`!isatty`), CI runners, and `stdout` redirection.
3. **Ad-Hoc Output Formatting:** Operations print directly to `stdout` or mutate UI state directly instead of returning typed domain outputs that can be rendered either as a TUI widget update or as a CLI table/JSON payload.

---

## 3. Design Principles and Non-Goals

### 3.1 Core Principles

- **Actions Are Domain Operations, Not UI Widgets:** The CLI is never auto-generated from visual components (`Button`, `Menu`). Visual hierarchy and CLI command taxonomy serve different ergonomics; only explicitly registered `Action`s become CLI commands.
- **Single Source of Truth for Input Schema and Validation:** An action's `Input` struct defines both its typed parameters (for TUI forms/invocation) and its `clap::Args` specification (for CLI parsing) alongside domain validation rules.
- **Strict Headless Isolation:** Executing a CLI subcommand must never allocate the `nyrui-core` component arena, enable raw mode, or touch the alternate screen buffer.
- **Runtime Command Tree Construction (No Codegen Build Step):** CLI commands are assembled at startup via trait implementations generated by proc-macros and `clap`'s derive/builder API, avoiding external `build.rs` source-file generation.

### 3.2 Explicit Non-Goals

- Replacing `clap` with a custom command-line parser. Nyrui delegates argument parsing, shell completions, and help generation directly to `clap`.
- Exposing pure UI state transitions (such as switching tabs, opening a modal, or moving focus) as CLI commands.
- Requiring every Nyrui application to expose a CLI; `nyrui-cli` is an opt-in feature/crate.

## 4. Architecture and Core Contracts

### 4.1 Architectural Overview

```text
                       ┌──────────────────────────┐
                       │   Binary Entrypoint      │
                       │  App::builder(ctx)...    │
                       └────────────┬─────────────┘
                                    │
                  ┌─────────────────┴─────────────────┐
                  │ argv has subcommand / flags?      │
                  ├─────────────────┬─────────────────┤
                  ▼ (No: Interactive)                 ▼ (Yes: Headless)
     ┌────────────────────────┐          ┌────────────────────────┐
     │      TUI Adapter       │          │      CLI Adapter       │
     │  - Raw mode & AltScr   │          │  - clap::Command match │
     │  - Component Arena     │          │  - FromArgMatches      │
     │  - Event Loop          │          │  - No TUI init         │
     └────────────┬───────────┘          └────────────┬───────────┘
                  │                                   │
                  └─────────────────┬─────────────────┘
                                    │ Input::validate()
                                    ▼
                       ┌──────────────────────────┐
                       │     ActionDispatcher     │
                       │  A::execute(&ctx, input) │
                       └────────────┬─────────────┘
                                    │ Result<A::Output, AppError>
                  ┌─────────────────┴─────────────────┐
                  ▼                                   ▼
     ┌────────────────────────┐          ┌────────────────────────┐
     │   TUI Result Handler   │          │   CLI Output Formatter │
     │  - Signal / State upd  │          │  - Table / Plain / JSON│
     │  - Error toast / modal │          │  - ExitCode mapping    │
     └────────────────────────┘          └────────────────────────┘
```

### 4.2 The `Action` Trait

Every shared operation implements the `Action` trait:

```rust
pub trait Action: 'static + Send + Sync {
    /// Unique static identifier (e.g., "identity.create").
    const ID: &'static str;

    /// Typed input parameters; implements `Validate` for shared domain checks.
    type Input: Validate + Send + 'static;

    /// Structured output returned on success.
    type Output: Send + 'static;

    /// Executes the operation asynchronously against the shared application context.
    fn execute<'a>(
        ctx: &'a AppContext,
        input: Self::Input,
    ) -> BoxFuture<'a, Result<Self::Output, AppError>>;
}
```

### 4.3 CLI Exposure Contract (`CliAction`)

An `Action` that should also be exposed on the command line implements `CliAction` (typically generated via `#[action(cli = "...")]`):

```rust
pub trait CliAction: Action
where
    Self::Input: clap::Args,
    Self::Output: CliOutput,
{
    /// CLI command path (e.g., `&["list"]` or nested `&["identity", "create"]`).
    const COMMAND_PATH: &'static [&'static str];

    /// Short description shown in `--help`.
    const ABOUT: &'static str;

    /// Optional command aliases (e.g., `&["ls"]`).
    const ALIASES: &'static [&'static str] = &[];
}
```

Using `Self::Input: clap::Args` means the exact same Rust struct used to dispatch the action in the TUI (or bound to a TUI `FormState<Self::Input>`) is parsed by `clap` on the command line.

### 4.4 Shared Input Validation (`Validate`)

Syntactic parsing (e.g., missing required flag or invalid integer literal) is handled by `clap` in the CLI and by field parsers in TUI forms. Semantic domain validation is unified via the `Validate` trait:

```rust
pub trait Validate {
    fn validate(&self) -> Result<(), ValidationErrors>;
}

#[derive(Debug, Default, Clone, Serialize)]
pub struct ValidationErrors {
    pub field_errors: BTreeMap<&'static str, Vec<SharedStr>>,
}
```

`ActionDispatcher::dispatch` always invokes `input.validate()?` **before** calling `A::execute`. Consequently:
- In the **TUI**, `ValidationErrors` maps directly by field name into `FormState` field error messages.
- In the **CLI**, `ValidationErrors` prints structured field diagnostics to `stderr` and exits with `ExitCode::from(65)` (`EX_DATAERR`).

### 4.5 Ergonomic Macro Declaration (`#[action]`)

To avoid repetitive trait boilerplate, the `#[action]` procedural macro in `nyrui-macros` generates the `Action` struct, `Input` struct (with `#[derive(clap::Args, Validate)]`), and `CliAction` implementation from an annotated async function:

```rust
/// List registered SSH identities.
#[action(
    id = "identity.list",
    cli = "list",
    aliases = ["ls"],
)]
pub async fn list_identities(
    ctx: &AppContext,
    /// Filter identities by provider name (e.g., github, gitlab)
    #[arg(long, short)]
    provider: Option<String>,
) -> Result<Vec<SshIdentity>, AppError> {
    ctx.ssh_service.list(provider.as_deref()).await
}
```

This single declaration produces:
1. `pub struct ListIdentities` implementing `Action` and `CliAction`.
2. `pub struct ListIdentitiesInput { pub provider: Option<String> }` deriving `Clone, Debug, PartialEq, clap::Args, Validate`.
3. Doc comments translated automatically into `clap` `--help` descriptions.

When a developer prefers explicit structs (for complex multi-field inputs shared with a TUI form), `#[derive(Action)]` can be applied directly to an explicit struct using a pre-defined `Input` type.

## 5. Output Formatting and Error Mapping

### 5.1 Structured CLI Output (`CliOutput`)

Actions never call `println!` directly. Instead, `CliAction::Output` implements `CliOutput`:

```rust
#[derive(Copy, Clone, Debug, Default, ValueEnum)]
pub enum OutputFormat {
    #[default]
    Table,
    Plain,
    Json,
}

pub trait CliOutput: Serialize {
    /// Renders human-readable tabular output when `--format table` is active.
    fn write_table(&self, writer: &mut dyn std::io::Write) -> std::io::Result<()>;

    /// Renders line-oriented plain text for shell piping (`awk`, `grep`, `xargs`).
    fn write_plain(&self, writer: &mut dyn std::io::Write) -> std::io::Result<()>;

    /// Renders JSON (`serde_json::to_writer_pretty`) when `--format json` is active.
    fn write_json(&self, writer: &mut dyn std::io::Write) -> std::io::Result<()> {
        serde_json::to_writer_pretty(&mut *writer, self)?;
        writeln!(writer)
    }
}
```

The CLI adapter automatically injects global `--format <table|plain|json>` and `--quiet` options onto the root `clap::Command`. Furthermore, if `stdout` is not a TTY (`!std::io::stdout().is_terminal()`) and `--format` was not explicitly specified, the formatter defaults to `Plain` (or disables ANSI table borders/colors) so shell pipelines receive clean output.

### 5.2 Unified Error Taxonomy and Exit Codes

All actions return `AppError`, which categorizes failures so both TUI and CLI adapters can react deterministically:

```rust
#[derive(Debug, thiserror::Error)]
pub enum ErrorKind {
    #[error("Validation error")]
    Validation(ValidationErrors),
    #[error("Resource not found: {0}")]
    NotFound(String),
    #[error("Conflict: {0}")]
    Conflict(String),
    #[error("Permission denied: {0}")]
    PermissionDenied(String),
    #[error("External service failure: {0}")]
    External(#[from] anyhow::Error),
}
```

| `ErrorKind` | TUI Presentation | CLI Behavior (`stderr` + Exit Code) |
| ----------- | ---------------- | ----------------------------------- |
| `Validation` | Highlights offending fields in active `FormState` | Prints field errors; exits `65` (`EX_DATAERR`) |
| `NotFound` | Shows warning toast / status message | Prints error message; exits `2` |
| `Conflict` | Shows inline conflict banner or modal | Prints error message; exits `3` |
| `PermissionDenied` | Prompts for elevation / credentials modal | Prints error message; exits `77` (`EX_NOPERM`) |
| `External` / Internal | Opens error notification with expandable details | Prints error chain; exits `1` |
| `clap` Usage Error | N/A | Standard `clap` usage help; exits `64` (`EX_USAGE`) |

## 6. Runtime Dispatch and Mode Selection

### 6.1 Application Bootstrap (`Application`)

An application wires its shared services, actions, TUI root component, and CLI configuration through `Application`:

```rust
#[tokio::main]
async fn main() -> std::process::ExitCode {
    let ctx = AppContext::new(SshService::load_default()?);

    Application::new("nysh", ctx)
        .version(env!("CARGO_PKG_VERSION"))
        .register_cli_action::<ListIdentities>()
        .register_cli_action::<CreateIdentity>()
        .register_cli_action::<DeleteIdentity>()
        .register_cli_action::<ActivateIdentity>()
        .register_action::<RefreshAgentStatus>() // TUI-only action (not exposed in CLI)
        .tui_root(|| ui! { NyshApp {} })
        .run()
        .await
}
```

### 6.2 Mode Resolution Rules

When `Application::run()` executes:

1. **Inspect `std::env::args_os()`:**
   - If no arguments are passed (or only TUI-compatible flags like `--theme`), `Application` initializes the `CrosstermBackend`, enters the alternate screen, mounts the `tui_root` component into the `nyrui-core` arena, and runs the TUI event loop.
   - If arguments match a registered CLI subcommand (or `--help` / `--version`), `Application` routes directly to the `CliAdapter` without ever initializing `crossterm` raw mode, alternate screen, or the component arena.
2. **TUI Action Dispatch (`ctx.dispatch`):**
   - Inside a TUI component, calling `ctx.dispatch::<DeleteIdentity>(DeleteIdentityInput { name }, Msg::IdentityDeleted)` spawns the action's future on the Tokio runtime with a clone of `Arc<AppContext>` and routes the `Result<Output, AppError>` back to the requesting `NodeId`'s `Component::update` method on the UI thread.

## 7. Crate Structure and Feature Flags

To allow CLI-only binaries or lightweight builds when needed while keeping full-featured applications ergonomic:

- `nyrui-core` defines the `Action`, `Validate`, `AppContext`, and `AppError` traits so TUI components and forms can interact with actions directly.
- `nyrui-cli` implements `CliAction`, `CliOutput`, the `clap` command tree builder, and the headless CLI runner.
- The top-level `nyrui` facade crate exposes feature flags:
  - `tui` (enabled by default): pulls in `nyrui-core`, `nyrui-widgets`, `ratatui`, and `crossterm`.
  - `cli` (enabled by default): pulls in `nyrui-cli` and `clap`.

## 8. Implementation Roadmap and Acceptance Criteria

### 8.1 Implementation Phases

| Phase | Scope | Deliverables |
| ----- | ----- | ------------ |
| **Phase 1: Core Action & Validation Contracts** | `Action` trait, `AppContext` container, `Validate` trait, `ValidationErrors`, `AppError` taxonomy, and `ActionDispatcher`. | Unit tests verifying typed dispatch and pre-execution validation failure short-circuiting. |
| **Phase 2: Headless CLI Adapter (`nyrui-cli`)** | `CliAction`, `CliOutput` (`Table`, `Plain`, `Json`), dynamic nested `clap::Command` assembly, TTY detection, and exit-code mapping. | Headless integration tests executing nested CLI commands, `--format json`, and verifying exit codes without terminal initialization. |
| **Phase 3: `#[action]` Macro & TUI Form Integration** | `#[action]` proc-macro in `nyrui-macros`, `ctx.dispatch::<A>()` integration in `nyrui-core`, and automatic `ValidationErrors` binding to `FormState`. | Reference app (`nysh`) running identical `list`, `create`, `delete`, and `activate` operations via both TUI views and CLI invocations. |

### 8.2 Acceptance Criteria

- [ ] A single `#[action]` definition can be invoked from a TUI component via `ctx.dispatch` and from the terminal via `<bin> <subcommand>`.
- [ ] Nested subcommands (e.g., `<bin> identity create`) are supported via `COMMAND_PATH`.
- [ ] Domain validation (`Validate`) executes identically for TUI form submissions and CLI invocations.
- [ ] Running a CLI subcommand does not initialize `crossterm` raw mode, alternate screen, or the TUI component arena.
- [ ] CLI output supports `--format table`, `--format plain`, and `--format json`, automatically degrading when `stdout` is piped.
- [ ] `AppError` variants map deterministically to documented non-zero exit codes in CLI mode and structured UI feedback in TUI mode.
